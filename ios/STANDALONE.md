# Standalone mode — build handoff

_Written 2026-10-07 · branch `feat/swift_ios` · decision: [ADR 0009](../docs/adr/0009-standalone-mode.md)_

This is the work plan for adding **Standalone mode** to the iOS app: the app
fetches the past week from arXiv itself and scores papers on the device, with no
digest service. Read this file top to bottom before writing code. The general app
handoff is [`HANDOFF.md`](HANDOFF.md); domain terms are in `CONTEXT.md`.

The work is meant to be done on a **Linux machine** (no Xcode). Everything in
the plan lives in the `ArxivDigestCore` Swift package, which builds and tests on
Linux. The few app-target edits are verified by CI on macOS.

---

## 1. Why, in one paragraph

Server mode needs an always-on machine the phone can reach. The user's available
Linux machine forbids long-running services, cron, and Tailscale, so for personal
use the app needs to work alone. The arXiv export API is plain HTTPS, so the phone
can fetch; what's missing is the Python engine. We port the pieces the app needs
to Swift and pin them to the Python engine with generated parity fixtures. Server
mode stays as the synced option. Full reasoning: ADR 0009.

## 2. Environment on the Linux machine

```bash
git clone https://github.com/isaac-tes/arxiv-digest.git && cd arxiv-digest
git switch feat/swift_ios

# Python side (engine, server, fixture scripts) — no sudo needed
curl -LsSf https://astral.sh/uv/install.sh | sh       # installs to ~/.local/bin
uv sync --group dev && uv run pytest                  # root suite (~290 tests, no network)
(cd server && uv sync --extra dev && uv run pytest)   # service suite

# Swift side: Swift 6.2 toolchain without sudo
#   swiftly (https://www.swift.org/install/linux/) installs into $HOME, or
#   use the official tarball and add its usr/bin to PATH.
cd ios && swift test                                  # Core suite
```

- Don't use `sudo`, cron, or background daemons on that machine; none are needed.
- **Linux Foundation quirks** (already handled in Core; keep it that way):
  - `URLSession` / `URLProtocol` need `#if canImport(FoundationNetworking) import FoundationNetworking #endif`.
  - `XMLParser` needs `#if canImport(FoundationXML) import FoundationXML #endif`.
  - Use `NSRegularExpression` (as `HighlightEngine` does), not Swift `Regex`
    literals, for consistent behaviour on both platforms.
  - No `os.Logger`, no Combine, no SwiftUI in Core.
- **App-target code** (`ios/Sources/ArxivDigestApp`) can't be built on Linux.
  Keep app edits small (section S2 lists them). Pushing to `feat/swift_ios` runs
  `.github/workflows/ios.yml`: it builds the app on macOS, runs `swift test` on
  macOS and Linux, and uploads screenshots (artifact **ios-screenshots**). Check it
  with `gh run list --branch feat/swift_ios` / `gh run view <id> --log-failed`, if
  `gh` is available and authenticated; otherwise ask the user to check Actions.

## 3. How the app is wired today (what you're plugging into)

- `AppModel` (`ArxivDigestApp/AppModel.swift`) has `enum Mode { case server, demo }`
  and builds an `APIClient` per mode in `makeClient(mode:url:)`. All screens talk
  only to `APIClient`, which speaks the digest service's JSON.
- **Demo mode** points `APIClient` at a fake host and a `URLSession` whose
  `protocolClasses = [DemoURLProtocol.self]`. `DemoURLProtocol` hands every request
  to `DemoBackend.shared.handle(method:url:body:)`
  (`ArxivDigestCore/Demo/DemoBackend.swift`), which implements the service's
  endpoints in memory:
  `/health`, `/digest`, `/digest/refresh`, `/removed` (+ `/restore`), `/config`
  (GET/PUT/PATCH, `/defaults`, `/presets`, `/presets/info`,
  `/presets/{name}/{load|merge}`), `/score`, `/zotero/status`, `/zotero/save`.
- `DemoBackend.view(timeframe:day:topN:)` is already a Swift port of the
  server's `digest_view` (ADR 0008): replacement filter, picked day, removed
  papers keep their ranking position, top-N. `score(_:)` already produces the
  GUI's rank / absence-reason wording.
- Demo data comes from `DemoFixture.swift`, generated by
  `ios/scripts/make_demo_fixture.py` from the real engine (invented papers and
  names). Its scores are precomputed, so they don't react to config edits; in
  Standalone, scores **must** react.
- Already ported and parity-tested (`Tests/ArxivDigestCoreTests/ParityTests.swift`):
  whole-word term matching, author matching including middle initials
  (`HighlightEngine.authorMatches`), highlight spans, arXiv ID parsing, exports.
  Reuse these in the scorer; don't write a second matcher.

## 4. Target design

```
AppModel.Mode: .server | .demo | .standalone
                                   │
APIClient ── URLSession(protocolClasses: [LocalURLProtocol]) ──┐
                                                                ▼
                        DigestRouter  (shared: routing, digest view, score wording,
                         ▲      ▲      presets/config endpoints, removals)
                         │      │
             DemoSource ─┘      └─ LiveSource
     (fixture papers +            (ArxivFetcher → papers, Scorer → scores,
      precomputed scores)          LocalStore → config/removed/cache on disk)
```

- Extract the routing and view logic out of `DemoBackend` into a shared type
  (name it `DigestRouter` or similar). Demo becomes "router + fixture source";
  Standalone is "router + live source". **Demo's behaviour and its tests must not
  change** (`DemoBackendTests.swift` is the guard).
- `handle` becomes `async` (live fetching is network I/O). In the URL protocol,
  start a `Task` in `startLoading()` and call `client?.urlProtocol(...)` when it
  finishes; handle `stopLoading()` by cancelling the task.
- Standalone answers with the **same JSON** the server returns. Compare against
  `server/app/schemas.py` and `server/app/routers/*.py` when in doubt; the
  server's tests (`server/tests/test_api.py`) show the expected shapes.

## 5. Work steps

Each step is a separate beads issue on the Mac (ids in brackets; beads data
isn't on GitHub). Do them in order; each one ends with green `swift test` and a
commit. Steps S1–S6 are the MVP; S7 and S8 need a decision from the user first.

### S1 — Swift scorer + parity fixture [`e85.1`]

- Port `arxiv_digest.explain_score` (≈ line 1383) and `score_paper` to
  `Core/Scoring/Scorer.swift`:
  `Scorer.explain(paper:config:) -> ScoreBreakdown` (the existing model in
  `Models/ScoreBreakdown.swift`, signals → `"keyword"`), `Scorer.score(...) -> Int`.
- Rules to reproduce exactly (read the Python, don't trust this summary):
  per-keyword and per-named-author weights from `cfg.weights`; author matching on
  the author field only; subject bonus from `cfg.feed_weights` using **substring**
  matching (a parent feed matches sub-categories); low-priority penalty applied
  once; long-abstract bonus; `word_boundary_matching` switches whole-word vs
  substring for keywords/authors/low-priority.
- `DigestConfig` must expose whatever the scorer reads (`weights`,
  `feedWeights`, `wordBoundaryMatching`, …); many accessors exist already.
- New script `ios/scripts/make_parity_fixture.py` (model it on
  `make_demo_fixture.py`): a handful of invented papers × several configs
  (defaults, word-boundary off, custom weights, feed weights incl. parent feed,
  low-priority hits, empty lists, unicode names) → expected `explain_score` output
  as JSON, written to `Tests/ArxivDigestCoreTests/ScoringParityFixture.swift`.
  Test: every case's Swift breakdown equals the Python one (terms, weights, totals).
- Invented names only (the repo is public; see `tests/test_presets.py`).

### S2 — Shared router + `Mode.standalone` [`e85.2`]

- Refactor per section 4 with Demo unchanged. Add `LiveSource`/`LocalBackend`
  behind it; until S3 lands, the live source can be backed by a stub fetcher so the
  wiring is testable.
- App target (keep it small, verified by CI):
  - `AppModel.Mode` gains `.standalone`; `makeClient` returns
    `APIClient(baseURL: LocalURLProtocol.baseURL, session: LocalURLProtocol.makeSession())`.
  - Settings → Connection: a third choice "On this device" next to Server and
    Demo, with one line of explanation (fetches from arXiv directly; first load
    takes ~10–40 s; not synced).
  - `LaunchOptions`: `-standalone` like `-demo`.
- `/health` returns `{"status":"ok","mode":"standalone"}` so the existing
  "Connected · … mode" label reads correctly.

### S3 — Past-week fetch from the arXiv export API [`e85.3`]

Port the API path of the engine's past-week fetch to `Core/Fetch/ArxivFetcher.swift`:

- `fetch_feed_api` (≈ line 1044): query
  `cat:<feed> AND submittedDate:[YYYYMMDDHHMM TO YYYYMMDDHHMM]`, last 7 days in
  UTC, `sortBy=submittedDate`, `sortOrder=descending`, page size 500, paginate
  until `opensearch:totalResults`, cap 2000.
- `_paper_from_api_entry` (≈ line 1101): id from `<id>` without version, authors
  joined with ", ", subjects from `<category term>`, abstract from `<summary>`,
  section = the API day label (`_api_day_label`).
- `_api_get_with_retry` (≈ line 917): descriptive `User-Agent` (reuse
  `_API_USER_AGENT`'s text), retry 429/5xx and transport errors, honour
  `Retry-After`, else exponential backoff from 3 s.
- `fetch_pastweek` API path: one category at a time, **3 s between requests**
  (`_ARXIV_RATE_LIMIT_SECONDS`), dedupe by id across feeds, surface failures as
  `notices` (the Digest model already has `notices`). Skip the HTML `/pastweek`
  fallback for now; if the API fails, report it in `notices`.
- Make sleeping injectable (a `sleep` closure or clock) so tests don't wait.
- Cache: raw fetch results keyed like the server (`timeframe` + sorted feeds),
  1 h TTL; `/digest/refresh` and pull-to-refresh bypass it.
- Tests (network-free): `MockURLProtocol` (already in the test target) serving
  recorded Atom pages. Record them once with the Python engine or `curl`, trim to
  a few entries, replace real author names with invented ones. Cover pagination,
  429 then success, dedupe across feeds, and parity of the parsed dicts against
  `_paper_from_api_entry` on the same XML (add those to the parity script).

### S4 — On-device storage, defaults, presets [`e85.4`]

- `LocalStore`: config, removed ids, and the fetch cache as JSON files in
  Application Support (on Linux tests: a temp directory injected via init).
  Atomic writes (`Data.write(options: .atomic)`).
- First run: the engine's default `Config()`, generated into a Core resource by
  the fixture script, the same defaults the CLI/GUI and server start from.
- Presets: generate `PRESETS` (description + config) from the engine the same
  way; `/config/presets*` behave as on the server.
- `/config/defaults`, PUT/PATCH semantics, and "explicitly empty list stays
  empty" (see commit `749a955`) must match the server.

### S5 — Score a paper by id [`e85.5`]

- Port `fetch_paper_by_id`: export API `id_list=<id>` (see `zotero_bridge.fetch_arxiv_atom`)
  → `_paper_from_api_entry` → `Scorer.explain`. Rank / absence reason come from the
  shared router (already written for Demo). Network failure → the same error the
  server returns (502 with a detail message).

### S6 — Announcement-day labels [`e85.6`]

The API's submission date isn't arXiv's announcement day; the GUI relabels papers
from the `/list/<feed>/pastweek?show=2000` HTML page (`_fetch_listing_day_labels`,
`_parse_listing_day_labels` ≈ line 988). Port that parser minimally (date headers
and the arXiv ids under each), keeping the API label as fallback when the page
fails. Parity test: run the Python parser and the Swift one on the same saved,
trimmed listing page (invent or strip names).

### S7 — "Today" feed (`/new`) [`e85.7`] — ask the user first

The engine scrapes the HTML `/new` page (`fetch_feed` ≈ line 673): New / Cross /
Replacement sections, then back-fills missing abstracts. Options to present:
(a) port the HTML parser with parity tests against saved pages; (b) use the
export API for the last ~1 day and derive "cross-list" from primary category
(no replacements). Until decided, Standalone offers **Past week only** and
`/digest?timeframe=today` returns a 422 with a clear message, like an invalid
timeframe on the server.

### S8 — Config sync across the user's devices [`e85.8`] — deferred

`NSUbiquitousKeyValueStore` would sync the small config JSON through iCloud, but
the iCloud capability needs a **paid** Apple Developer membership; a free
personal team can't sign it. Don't start this without the user's go-ahead.

## 6. Rules and pitfalls

- **No live network in tests.** Everything goes through `MockURLProtocol` or
  injected closures; CI runs on Linux and macOS.
- **Parity over cleverness.** When Swift and Python disagree, Python is right;
  change Swift. If the Python behaviour looks wrong, note it for the user rather
  than "fixing" it in Swift only.
- **Don't change the server's JSON contract** for Standalone's convenience.
- **Demo mode stays as it is** (screenshots in CI depend on it).
- **Public repo:** invented names in fixtures, no personal data, no beads/Dolt
  data pushed (`refs/dolt/data` stays off GitHub). Don't run `bd dolt push`,
  `bd sync`, or `bd init` on the Linux machine.
- Conventional Commits (`feat(ios): …`, `test(ios): …`) per `CONTRIBUTING.md`,
  small commits per step, push to `feat/swift_ios`, then check the CI run.
- Update `CONTEXT.md` (Standalone term exists), `HANDOFF.md` ("What the app does"
  table and Remaining work), and this file's progress log as steps land.

## 7. Done when (MVP = S1–S6)

- Settings → Connection → **On this device** loads a real past-week digest on the
  simulator/phone with no server running.
- Editing keywords/authors/weights and saving re-ranks the digest (scores react).
- Day chips, removals, Restore, top-N, Score-a-paper (rank / absence reason)
  behave like Server mode.
- `swift test` green on Linux and macOS; parity fixtures regenerate cleanly from
  the engine; CI iOS job green with screenshots.
- On the Mac the user runs it on the phone (see `HANDOFF.md` → "Try it on a Mac").
